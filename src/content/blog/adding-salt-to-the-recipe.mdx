<Dropcap letter="T">wo users typing the identical password walk away with the identical hash. That single, simple fact was enough to make an attacker's job trivial: crack one digest, and every account anywhere in the stolen database that reused the same password falls with it.</Dropcap>

```text
[ Alice: "Password123" ] ---> [ SHA-256 ] ---> "ef92b778bafe771e..."
[ Bob:   "Password123" ] ---> [ SHA-256 ] ---> "ef92b778bafe771e..."
```

To stop a single lookup table from cracking an entire database at once, every stored hash needs to come out unique, even when two people pick the literal same password.

The fix already existed in 1976. Robert Morris Sr. and Ken Thompson's original <span class="code-inline">crypt(3)</span>, the same function that introduced password hashing in the first place, mixed in a small random value before hashing, specifically to stop identical passwords from producing identical output. It used twelve bits of randomness, 4,096 possible values, which a modern GPU chews through without slowing down. The idea was right from the start. The scale wasn't.

## The salting workflow

A salt gets combined with the plaintext password before either one ever reaches the hash function:

```text
[ Plaintext: "Password123" ]  +  [ Random Salt: "k8#9xQ" ]
                              |
                              v
             [ Combined: "Password123k8#9xQ" ]
                              |
                              v
                      [ Hash Algorithm ]
                              |
                              v
             [ Stored Hash: "4a1f8c09e3..." ]
```

```text
DATABASE RECORD:
---------------------------------------------------------------------------------
USER    SALT         STORED HASH (Salt + Password)
---------------------------------------------------------------------------------
alice   k8#9xQ  ---> 4a1f8c09e3bb8a72c1d9... (Result of "Password123k8#9xQ")
bob     m3$7vL  ---> d88e9102ca17482f09a1... (Result of "Password123m3$7vL")
---------------------------------------------------------------------------------
```

- **The salt is public**: it sits right next to the hash in the database in plain text, and it doesn't need to hide. Its whole job is making every row different, not staying secret.
- **Tables stop working**: a table built for <span class="code-inline">Password123</span> alone is useless the moment every user's password gets combined with a different random string first. Cracking Alice now needs a table built specifically for her salt, and Bob's needs an entirely separate one.
- **The cost explodes**: precomputing separate multi-terabyte tables for billions of possible salt values isn't a shortcut anymore. It's the same amount of work as attacking every account one at a time, which is exactly what salting is designed to force.

## The speed problem: why fast hashes still fail

Salting neutralized rainbow tables, and attackers pivoted straight to raw hardware.

```text
Algorithm: SHA-256 (Designed for network speed)
GPU Cluster Capability: 100,000,000,000 guesses / sec
Result: An 8-character salted password falls in minutes.
```

Salted or not, MD5 and SHA-256 were built for a different job: verifying a large file or a network packet in nanoseconds. That's precisely the wrong property for a password check, where speed benefits the attacker guessing, not the user logging in.

## Key derivation functions: hashing on purpose, slowly

Password-specific hash functions add two tunable dials that general-purpose hashes never had:

1. **Work factor**: instead of hashing once, algorithms like bcrypt and PBKDF2 run the operation tens or hundreds of thousands of times in a loop. A hundred-millisecond delay is invisible to someone logging in once. Multiplied across billions of guesses, that same delay drops an attacker from billions of guesses a second to a few hundred.
2. **Memory hardness**: Argon2 and scrypt demand a real chunk of RAM, sixty-four megabytes or more, to compute a single hash. A GPU or a custom cracking chip packs thousands of tiny cores with almost no cache memory each, so starving every guess of RAM starves the exact hardware advantage that made GPU cracking worthwhile.

Niels Provos and David Mazières built bcrypt around this idea in 1999. Argon2 won the Password Hashing Competition in 2015 by pushing the memory-hardness dial further still.

<span class="highlight">Salt stopped attackers from cracking everyone at once. Slow hashing stopped them from cracking anyone quickly.</span>

<DetectionOpportunity>A fast algorithm and a slow one can protect the exact same password and produce wildly different outcomes under an offline attack. Salting alone won't save a system that still reaches for MD5 or plain SHA-256 for password storage. The algorithm itself has to be slow on purpose.</DetectionOpportunity>

> Security here isn't about hiding the math. It's about making the math expensive.

Salting and slow hashing finally secured identity at rest, inside the database, against bulk offline cracking. The fight simply moved back to where it started a few posts ago: the connection itself. Two machines that have never met, talking across a hostile internet, still have to agree on a secret while an eavesdropper listens to every word they exchange. That question is what the digital handshake, TLS, was built to answer.
