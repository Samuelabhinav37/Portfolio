faqs:
  - q: "What is a cryptographic hash function?"
    a: "A one-way mathematical function that turns any input, a password, a file, an entire book, into a fixed-length string called a digest. Feed it the same input twice and you get the same digest every time, but there's no operation that runs backward from the digest to the original input. A server can use that digest to check a password without ever holding the password itself."
  - q: "How is hashing different from encryption?"
    a: "Encryption is two-way by design. Whoever holds the key can decrypt a ciphertext back into the original data, which is exactly what you want for data that needs to be read again later. Hashing throws that reversibility away on purpose. There's no key that unblends a hash back into its input, which is exactly what you want for a password a server should never need to see twice."
  - q: "What is the avalanche effect in hashing?"
    a: "A property that says a tiny change to the input, even flipping one letter's case, must scramble the output completely. Hash \"password\" and \"Password\" and the two digests share nothing recognizable in common. Without this, similar passwords would produce similar-looking hashes, and an attacker could narrow down guesses just by watching how close a digest looks to another one."
  - q: "Why can't a hash be reversed back into the original password?"
    a: "Because a hash function throws away information on purpose. Many different inputs can technically map to outputs of the same fixed length, so there's no unique mathematical inverse to run. The only real way back is to guess an input, hash it, and see if the result matches, which is exactly what a dictionary attack or a rainbow table is built to automate."
  - q: "If a database of hashed passwords gets stolen, are the passwords safe?"
    a: "Safer, not safe. A stolen hash isn't a stolen password, but a deterministic hash function always produces the same digest for the same input, and that's a lever an attacker can pull. Pre-computed lookups against common passwords can turn a stolen hash back into cleartext without ever running the hash function against a live server. That gap is exactly what the next layer of password storage, salting, was built to close."

## Fruit smoothie problem

Hashing only makes sense next to what it replaced:

- **Encryption (two-way)**: sealing an apple in a locked lunchbox. Whoever holds the key opens it and gets the exact same apple back.
- **Hashing (one-way)**: dropping that same apple into an industrial blender. What comes out is purée, and no amount of computing power runs a blender backward into a whole apple again.

```text
                   TWO-WAY ENCRYPTION
[ Data: "Apple" ]  <===================>  [ Ciphertext: "7x9$zQ2" ]
                       (With Key)

                    ONE-WAY HASH FUNCTION
[ Data: "Apple" ]  -------------------->  [ Hash Digest: "3a8f9c1..." ]
                      (Blender Only)
                      (Cannot Reverse)
```

## Four rules every hash function has to follow

Not every math operation earns the name "cryptographic hash." A real one holds to four strict properties:

1. **One-way**: computing <span class="code-inline">hash(x)</span> from <span class="code-inline">x</span> is trivial. Recovering <span class="code-inline">x</span> from the hash alone is not, by design.
2. **Deterministic**: the same input always produces the same output. Hash <span class="code-inline">Password123</span> a billion times through SHA-256 and every run produces the identical 64-character digest.
3. **Fixed output length**: a single letter and the entire text of *War and Peace* both come out the same fixed size, exactly 256 bits for SHA-256, regardless of how much you fed in.
4. **The avalanche effect**: changing one character anywhere in the input scrambles the entire output.

```text
Input:  "password"  --->  5e884898da28047151d0e56f8dc6292773603d0d6aabbdd62a11ef721d1542d8
Input:  "Password"  --->  e7cf3ef4f17c3999a94f2c6f612e8a888e5b1026878e4e19398b23bd38ec221a
```

<span class="highlight">Hashing didn't hide the secret. It got rid of the need to keep one at all.</span>

## Login handshake

A working hash function turns password storage into a matching exercise instead of a filing cabinet:

```text
1. USER REGISTRATION:
   User Input ("Secret") ---> [ Hash Function ] ---> Stored in DB ("8d969eef6...")
   (Original password is immediately discarded)

2. USER LOGIN:
   User Enters ("Secret") ---> [ Same Hash Function ] ---> Generates ("8d969eef6...")
                                                                   |
                                                      [ Compare DB vs New Hash ]
                                                                   |
                                                          Match? ---> Access Granted
```

Breach a database built this way and an attacker doesn't walk out with a list of readable credentials. They walk out with a list of digests, and a digest by itself unlocks nothing.

<DetectionOpportunity>Not every one-way function belongs in a login flow. General-purpose hashes like MD5 or plain SHA-256 run fast, which is exactly wrong for password storage: a modern GPU can push billions of guesses through them per second. Purpose-built password hashes like bcrypt, scrypt, and Argon2 exist specifically to slow that math down instead of speeding it up.</DetectionOpportunity>

> A stolen hash isn't a stolen password. It's a math problem, and math problems take time.

Hashing solved the server-side dilemma, but its own greatest strength doubled as a new weakness. Run the same password through the same function and you always get the same digest, which means an attacker can precompute hashes for the ten million most common passwords once, offline, and check a stolen database against that list in seconds. That shortcut is what dictionary attacks and rainbow tables exploit, and it's what forced the next generation of password storage to add the one thing hashing alone never had: randomness.
