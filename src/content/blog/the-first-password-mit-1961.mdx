<Dropcap letter="I">n the late 1950s, using a computer felt like waiting in line for a public photocopy machine. A mainframe filled an entire room, cost millions of dollars, and processed exactly one person's stack of punched cards at a time. You handed your deck to an operator, walked away for four hours, and hoped you hadn't made a single syntax error.</Dropcap>

Everything changed in 1961, when MIT switched on the Compatible Time-Sharing System, CTSS, running on an IBM 7094. CTSS sliced the processor's attention into milliseconds and rotated through dozens of remote terminals so fast that thirty researchers could work the same machine at the same moment, each one unaware the others were even there.

```text
[ Researcher A ] ---> [ Wait in Line ] ---> [ Single Mainframe ] ---> [ 4-Hour Delay ]
```

## Shared disk, shared risk

Time-sharing solved the waiting-line problem and immediately created a new one. All thirty users read from and wrote to the same physical disk.

```text
[ User: Alice ] \
[ User: Bob   ]  ---> [ Shared Disk Drive ] ---> [ Unrestricted File Access ]
[ User: Carol ] /
```

Sit down at any terminal and you could overwrite Alice's research or wipe someone else's operating system code, by accident or on purpose. Every account also carried a strict weekly runtime budget, four hours for most researchers, and with no way to tell users apart, Bob could burn Alice's entire allowance running his own simulations.

<Mnote day="1961" sub="Corbat&oacute; writes the gatekeeper script" />CTSS project lead Fernando Corbató answered this with a short login script:

1. **Identify**: the terminal asks for a username.
2. **Authenticate**: it prompts for a secret word.
3. **Verify**: CTSS checks the input against the User File Table.
4. **Isolate**: a match hands the user their own private directory and starts tracking their CPU time.

<span class="highlight">The digital password was born, and it wasn't built to survive an attacker. It was built to keep polite colleagues out of each other's folders.</span>

## The fatal flaw: a cleartext master file

Corbató's team wasn't defending against a nation-state. They were keeping friendly university researchers out of each other's directories, and that assumption shaped a real design flaw: the UFT stored every password as plain, unencrypted text.

```text
----------------------------------------
| USERNAME    | PASSWORD    | TIME LEFT|
----------------------------------------
| CORBATO     | SECRET1     | 40.0 HRS |
| J_DOE       | BEANTOWN    | 12.5 HRS |
| A_SMITH     | REDSOX      | 05.0 HRS |
----------------------------------------
```

Read that file once and you owned every credential on the machine.

<DetectionOpportunity>A credential store that can print its own contents by accident is a breach waiting on a typo, not a targeted attacker. Hash and salt what you store, and a leaked file stops handing out live secrets on its own.</DetectionOpportunity>

## The first credential breach (1962)

<Mnote day="1962" sub="a message-of-the-day bug exposes the UFT" />An editing session on CTSS's message-of-the-day file hit a buffer-swap bug. Instead of printing the daily system greeting, it dumped the entire cleartext master password file straight onto the terminal of whoever logged in next.

That user was Allan Scherr, a CTSS researcher. He watched every password on the machine scroll past, wrote them down, and logged into the administrator's account to grant himself extra runtime, enough to play games and run his own thesis simulations without waiting his turn.

> The first credential breach in computing history came from an application bug exposing an unhashed text file, not a sophisticated attack.

## The modern takeaway

MIT's 1961 shortcut still sits underneath how identity works today: prove you know a shared secret, and the system trusts you.

Corbató's shortcut worked fine for a closed lab of researchers who mostly trusted each other, but it left behind one urgent question that would occupy the next thirty years of computer security: how do you verify a password without ever storing the password itself somewhere a bug, or an attacker, could read it? Answering that question is what brought real cryptography into computing.
