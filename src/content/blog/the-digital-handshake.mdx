  - q: "What problem does the TLS handshake actually solve?"
    a: "Two machines that have never met need to agree on a shared encryption key across a network full of eavesdroppers, without ever sending that key where an eavesdropper could grab it.   - q: "How does Diffie-Hellman key exchange work without sending the secret key?"
    a: "Each side combines a public, openly shared value with a private value only they hold, and sends the result across the wire. 1976 turns out to be a busy year for this series. The same year Unix started hashing and salting passwords, Diffie and Hellman solved a completely different problem across the country: how to agree on a secret with a stranger in plain sight of an adversary.

## Mixing paint: the key exchange trick

The math behind Diffie-Hellman behaves a lot like mixing paint:

- **Public base**: client and server publicly agree on a starting color, yellow. Anyone watching knows it.
- **Private secrets**: the client secretly picks red, the server secretly picks blue, and neither color ever leaves its own machine.
- **The mix**: the client mixes yellow with red and sends orange across the network. The server mixes yellow with blue and sends green.
- **The shared secret**: the client adds its private red to the green it received and gets brown. The server adds its private blue to the orange it received and lands on the identical brown.

```text
[ Client Secret: Red ]                               [ Server Secret: Blue ]
         |                                                     |
  Mix with Public Yellow                                Mix with Public Yellow
         |                                                     |
         v                                                     v
   Sends: ORANGE =====================================> Receives: ORANGE
   Receives: GREEN <===================================== Sends: GREEN
         |                                                     |
  + Add Private Red                                     + Add Private Blue
         |                                                     |
         v                                                     v
[ FINAL SHARED KEY: BROWN ]                           [ FINAL SHARED KEY: BROWN ]
```

An eavesdropper on the wire only ever sees yellow, orange, and green. Pulling red back out of orange means reversing modular exponentiation over a large prime, and the discrete logarithm problem gives no practical shortcut for that. Both machines land on the same brown without either one ever sending it.

## The impersonation flaw: who are you actually talking to?

Key exchange solves confidentiality. It solves nothing about identity, and that gap has a name: the man-in-the-middle attack.

```text
[ Client ] <--- (Tunnel 1) ---> [ Attacker / MitM ] <--- (Tunnel 2) ---> [ Real Bank ]
```

An attacker who intercepts the connection early enough runs a key exchange with the client while pretending to be the bank, and a separate key exchange with the real bank while pretending to be the client. Both tunnels look perfectly encrypted. Neither one connects the two people who actually meant to talk.

- **The certificate**: the server presents a signed certificate holding its public key and its domain name.
- **The signature**: a trusted Certificate Authority, Let's Encrypt or DigiCert among them, has already signed that certificate after verifying the server controls the domain.
- **The trust anchor**: the browser ships with the CAs' own public keys built in, so it verifies that signature instantly, no separate lookup required.

<span class="highlight">Diffie-Hellman solved who can listen. Certificates solved who you're actually talking to.</span>

## The handshake itself

```text
CLIENT                                                               SERVER
  |                                                                    |
  | -------- 1. ClientHello (TLS Version, Supported Ciphers) --------> |
  |                                                                    |
  | <------- 2. ServerHello (Chosen Cipher, Digital Certificate) ----- |
  |                                                                    |
  |  [ Client verifies CA signature on Certificate ]                   |
  |  [ Both generate ephemeral keys via Key Exchange ]                 |
  |                                                                    |
  | <====== 3. Session Keys Generated -> Encrypted Tunnel Active =====> |
  |                                                                    |
  | -------- 4. HTTP GET /login (Fully Encrypted Application Data) --> |
```

1. **Hello exchange**: client and server agree on a TLS version and a cipher suite.
2. **Authentication**: the server presents its signed certificate, and the client checks it against its trusted CA store.
3. **Key generation**: both sides run the key exchange math independently and land on the identical symmetric session key.
4. **Secure transmission**: the handshake ends, and every request and response after it travels inside a fast, symmetrically encrypted tunnel.

The whole exchange finishes in under fifty milliseconds, before a single byte of your actual request ever leaves the client.

<DetectionOpportunity>A valid certificate only proves the server holds the private key matching its public one and that a CA vouched for the domain. It says nothing about whether that domain is the one your user actually meant to visit. Certificate pinning and HSTS exist specifically to close the gap between "this certificate is valid" and "this certificate belongs to who I think it does."</DetectionOpportunity>

> A handshake doesn't just start a conversation. It decides whether that conversation can be trusted at all.

Every certificate and every key exchange in this handshake leans on the same underlying trick: two mathematically related keys that do different jobs, one that locks and one that unlocks, without either one ever revealing the other. That asymmetry is the actual engine underneath TLS, and it's worth taking apart on its own terms.
