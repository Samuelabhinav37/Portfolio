## The problem

Most home SOC labs prove that tools were installed. I wanted one that proves detections work. That means a rule is not done when it parses. It is done when a real attacker technique has fired it, the alert has landed, and I have written down how long that took.

So Sentinel treats detections as code. Each rule is written once as Sigma, tagged to MITRE ATT&CK, and kept in Git. CI checks it on every change. Then it gets deployed to Elastic and fired at for real.

Elastic is the one SIEM that runs live. Splunk is a second Sigma compile target, used only to prove the rules are portable. Wazuh, Suricata and Zeek add host and network telemetry. Everything sits on three VMs reached over Tailscale. The only open ports are SSH and Tailscale itself.

The same Terraform builds the stack on Oracle Cloud and ports to Azure and AWS. Those two also get a small Linux attack target. It enrolls itself into the live SIEM, so I can fire the same detections from more than one cloud.

## Proving each rule

Every one of the 18 rules has been caught firing on a real command. Linux rules were fired live on the monitored host, using the Atomic Red Team test where one exists. Windows rules used replayed attack telemetry from OTRF's Mordor datasets, plus hand-built events where no sample existed.

That testing found bugs that syntax checks never would:

- The encoded-PowerShell rule had a regex anchoring bug. Synthetic events caught it.
- One rule was modelled on a service that does not exist on the host's actual architecture.
- Two rules were silently broken by `update-alternatives`. The binary I invoked resolved to a different path than the one the rule matched.

CI now carries regression tests for the regex bugs. A detection change also needs a negative control before it is accepted.

## Two models, one gate

When a rule fires, Kibana calls an n8n webhook. n8n sends the alert to two models at once with the same prompt. One is `llama3.2:3b`, running locally on Ollama. The other is Claude Haiku 4.5. With the single-model version, alert to written verdict took 67 seconds, almost all of it inference.

Automated response only happens on agreement. Both models must rate the alert high or critical, with a low chance of false positive. One model alone can never trigger it. Every alert also records whether the two agreed. The disagreements become a filterable queue for a human.

The responder itself is deliberately narrow. It is off by default and bound to one host. Before it kills anything, it re-fetches the stored alert and checks host, PID, process start time and executable. It signals through a Linux `pidfd`, so a recycled PID can't be hit by mistake. Protected processes are refused, and an alert can't be acted on twice.

  The useful output of two-model triage isn't the cases where they agree. It's the cases where they don't. Those alerts are where a rule is too broad, or where the models are guessing, and they're exactly what a human should look at first.

## Beyond the pipeline

- **MCP server.** One interface over alert search, triage lookup, Wazuh agent state, ATT&CK coverage and the response trigger. Each tool is annotated read-only or destructive, so a client can tell which calls are safe to auto-approve. Only the response trigger is destructive.
- **Detection advisor.** A script that reads the disagreement queue and drafts rule changes into a drafts folder. Nothing it writes is live until it passes the same validation loop as any other rule.
- **Right-sized lab profile.** Real `docker stats` numbers showed the stack was about three times over-provisioned. Elasticsearch and Shuffle's bundled OpenSearch heaps were most of it. A lab profile now trims them, and it is always an explicit opt-in.

## What's not finished

The recorded deployment was on Oracle Cloud. The newest work (the MCP server, two-model triage and the hardened responder) is integrated and passes its tests locally: 67 Python tests, the n8n workflow regression tests, Terraform validation on all three clouds and Compose config checks. It has not been redeployed and live-fired yet. Cloud and Windows targets support detection and triage, but not remote kills. Velociraptor is configured server-side and stubbed until a client is enrolled.
